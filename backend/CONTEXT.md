# Domain Context

Architecture vocabulary lives in reviews; model vocabulary lives in `docs/model_blueprint.md`. This file records domain terms and workflow facts that name good seams. Architectural decisions are recorded in `docs/adr/` — see **ADR-0001** (isolate the Minutes Engine, push all I/O to the boundary) before proposing minutes-related refactors, **ADR-0002** (CQRS-lite: write-only repository, read-only views, season-scoped keys) before touching persistence, **ADR-0003** (immutable Rulebook via dependency injection; no global scoring state, ever) before touching scoring rules, and **ADR-0004** (one projection core, many data adapters; orchestration lives in `run_projection_stages` only, adapters only gather and map) before touching projection orchestration. Backend refactoring is **paused** after ADR-0004; Candidate #4 (historical_validation split) is deferred, and current work is the Admin Panel frontend.

## Workflow

- **Weekly Run** — every gameweek the model is run and produces a fresh set of CSVs. This is a permanent weekly cadence, not a migration artifact.
- **Weekly CSV Drop** — the CSVs generated by the Weekly Run. These are a real interface: consumed downstream by the website (legacy filenames/column order in `outputs/legacy_live/`) and by the **Admin Panel**.
- **Admin Panel** — the admin UI. Each week the Weekly CSV Drop is uploaded/updated there **manually** by a human. It is a second consumer of the export interface (two consumers = the export seam is real, keep filenames and column order stable). Its model-side integration is the **Admin API** (`src/fpl_xpts/api.py`, `uvicorn fpl_xpts.api:app`): `POST /api/v1/admin/projections/run` takes `manual_minutes` + `overrides` JSON, validates against the Minutes Contract (violations → 400 with field errors), and executes the in-memory route with the bundle cached at startup and `write_snapshot=False`. With `save_as_draft: true` (+ required `season`), results persist via the injected `ProjectionRepository` and the response carries `run_id`; `POST /api/v1/admin/projections/runs/{run_id}/publish` flips the dashboard's `published_*` views to it (404 unknown, 409 archived). Persistence wiring: `DATABASE_URL` env var → psycopg connection pool in the lifespan → request-scoped repository via `get_optional_repository`/`get_repository` (fail-closed 503 when unconfigured; previews work without a DB). Auth: `X-Admin-Token` shared secret via `ADMIN_API_TOKEN` env var — **fail-closed** (503 when unconfigured). API tests inject `FakeProjectionRepository` through one `dependency_overrides` entry — no DB required. Guarded by `tests/test_api_endpoints.py`.
- **Manual Minutes Inputs** — human-edited CSVs (expected minutes, availability judgment calls) fed into the model each week. Manual-by-exception is a first-class, recurring input — not a temporary patch. Any deepened Minutes module must accept weekly manual inputs through its interface.
- **Minutes Contract** — the strict per-row schema for Manual Minutes Inputs (`src/fpl_xpts/minutes_contract.py`: `PlayerMinutesState`, `MinuteOverrideState`). Files are validated at the seam *before* a run; a bad weekly edit fails loudly with CSV line numbers instead of being silently coerced. Path resolution lives in `resolve_manual_minutes_paths` / `resolve_minute_override_paths` — the legacy `player_minutes_inputs_gw37_to_38.csv` fallback and the `minute_overrides.csv` auto-discovery names are named constants there, not magic strings in the pipeline.
- **Minutes Engine** — the pure precedence core (`src/fpl_xpts/minutes_engine.py`: `resolve_minutes`). Owns layers 2–5 (trained model → manual inputs in order → hard overrides) and performs **no I/O**: the model bundle arrives pre-loaded, manual/override states arrive contract-validated. Layer 1 (heuristic baseline, `xpts.build_player_fixture_forecast`) and layer 6 (`xpts.recompute_player_fixture_components`) sit outside it in the pipeline. Precedence rules: later manual files beat earlier ones; overrides pin `expected_minutes` only (probabilities keep their lower-layer values). Tested layer-by-layer in `tests/test_minutes_engine.py`, including a purity guard. **Frozen.**
- **Minutes Run Inputs (the Admin Panel API seam)** — `resolve_minutes_run_inputs` / `MinutesRunInputs` in `minutes_contract.py`: the single boundary where minutes inputs are resolved per run. Two mutually exclusive adapters per input: **file route** (CSV paths or legacy auto-discovery — used by CLI `--manual-minutes` / `--minute-overrides`, cron, notebooks) and **in-memory route** (`manual_minutes_states` / `minute_override_states` on `run_live_projection` — the Admin Panel path; raw JSON dicts coerce through the contract). The in-memory route performs zero file I/O: pass `minutes_model_bundle` (pre-loaded) and `write_snapshot=False`. All path/CWD knowledge terminates at this boundary — nothing downstream touches a path. Guarded by `tests/test_pipeline_api.py` with I/O tripwires.

- **Rulebook** — FPL scoring rules as one frozen value (`src/fpl_xpts/rulebook.py`: `Rulebook`, `CURRENT_RULEBOOK`, `rulebook_for_season`). Point values, penalty constants, bonus proxy weights, MC BPS weights, and era flags live here; `scoring.py`/`bonus.py` are thin reads of `CURRENT_RULEBOOK` with legacy signatures. Era knowledge (GK goals 6→10 in 2024-25, DEFCON from 2025-26, BPS/assist versions) is in the library, not the replay script. **Phase 3 state:** the seam is complete for live + replay. All engine entry points accept `rulebook: Rulebook = CURRENT_RULEBOOK` and read rules **only** from the injected value — `xpts.py` and `monte_carlo.py` no longer import the scoring functions at all (nothing left to monkeypatch). `season_scoring_context`, `get_season_scoring_config`, and the hand-maintained BPS mirrors are **deleted** from the replay; it resolves `rulebook_for_season(season)` once per season and injects it into `build_player_fixture_forecast`, `recompute_player_fixture_components`, and both `simulate_player_week` calls. Era swapping is concurrency-safe (a value, not global mutation). `scoring.py` remains as the current-rules convenience interface (rulebook-backed, used by tests) plus `POSITION_BY_ELEMENT_TYPE`. **Phase 4 (arc complete):** backtests are era-aware — season-looping functions (`run_holdout_backtest`, `sweep_form_weight`, `write_backtest_outputs`, `apply_production_formula_by_season`) default to `rulebook=None`, meaning *resolve `rulebook_for_season(season)` per season group* (train/test can span rule eras); an explicit rulebook forces one rule set (shadow comparisons). The GK era bug is **fixed and quantified** (`scripts/quantify_gk_bug.py`, 2022-23: −0.971 xPts across all GKs — the only affected channel through the backtest formula is GK goal points × GK xG; DEFCON-era differences don't flow through it because the formula has no defcon component). Inline MC BPS numbers (assist 9, CS 12, saves 2, appearance 6/3, positional baselines) are simulation heuristics, not yet rulebook fields — future candidate.
- **Projection Core** — the single stage-sequence implementation (`pipeline.run_projection_stages`): forecast (L1) → Minutes Engine (L2–5) → component recompute (L6) → gameweek aggregation → Monte Carlo → tail attach. Consumes only a **`ProjectionInputs`** contract (frozen dataclass in `pipeline.py`: `players`, `teams`, `fixtures_forecast`, `history_by_player`, `rulebook`, `minutes_inputs`, `minutes_model_bundle` — column schemas documented on the class) plus model knobs from config; performs no network or file I/O. `run_live_projection` is now the **Live Adapter**: acquisition (FPL API, Understat, odds, Elevenify), minutes-input resolution + bundle load (ADR-0001 boundary), then one core call; ML attach and snapshot writing stay adapter-side. **Candidate #3 Phase 2 state:** the historical Data Adapter exists (`retrospective_replay.build_historical_inputs` — vaastav frames → `ProjectionInputs`, empty manual minutes, era rulebook) and the shadow test (`shadow_core_diff_for_gw`) ran legacy-vs-core side by side. **Measured drift (systematic, replicated across 2023-24 GW2 and 2024-25 GW10):** the core's `expected_minutes` are ~3.5–4.6 min lower on average (max ~8), xPts ~0.10–0.15 lower on average (max ~0.97), same trained bundle both sides. Root cause: the core's minutes stage builds features via `build_live_minutes_features` from adapter history (round/minutes/starts/kickoff only), while the legacy replay scores **purpose-built historical features** (`build_historical_minutes_features`: availability, standings, fixture congestion) — a feature-fidelity gap, not an engine bug. **Candidate #3 COMPLETE (Phase 4, the purge):** the replay drives the unified core exclusively — `_run_gw` = historical Data Adapter (`build_historical_inputs`: era rulebook, empty manual minutes, element-summary-shaped history, `_prepared_minutes_features` through the L2 seam) → `run_projection_stages` → replay-unique analysis (padded + ML-weighted MC with bespoke seeds, hence `include_mc=False` on the core; actuals join; metrics). `derive_replay_minutes`, `apply_replay_minutes`, the legacy L1/L6 stage sequencing, and the shadow harness are **deleted** (zero-drift equivalence was proven first; end-to-end smoke on real 2023-24 GW2 reproduced the shadow's exact values). Minutes *reporting* columns now read off the core's resolved `player_fixture` (`_minutes_report_from_player_fixture`) — a deliberate reporting change: fallback players report their resolved heuristic values instead of NaN, and bundle-internal extras (`pred_mins_if_start`/`_if_sub`/`start_given_play`) no longer appear in outputs. The L2 feature seam (`ProjectionInputs.minutes_features`; `None` = live building) is guarded in `test_minutes_engine.py`; the adapter is regression-guarded in `test_retrospective_replay.py`. The stage sequence now exists **once**, in `pipeline.run_projection_stages`, behind one contract, with two production adapters (live, historical). Remaining candidate-#3-adjacent debt: the replay still imports `historical_validation`/`market_odds` underscore-helpers for *acquisition* — promoting those into a named historical-source interface is Candidate #4 territory.
- **Published Run** — the persistence/publishing model (`db/migrations/0001_initial_schema.sql`, `src/fpl_xpts/projection_repository.py`, `src/fpl_xpts/postgres_repository.py`). A projection run is saved append-only as a **draft**, then **published**; the public dashboard reads only the `published_*` views, which resolve "latest published wins" by `published_at`. Runs are immutable after save — corrections are a new run; rollback is republishing an earlier run. The `ProjectionRepository` protocol is the write contract; the SQL views are the read contract — the dashboard never reads through Python. Tests use `tests/fakes.py::FakeProjectionRepository`, which passes the same contract tests as the Postgres adapter.
- **Season** — FPL recycles player/team/fixture ids every season, so every dimension row is keyed by `(season, fpl_id)` (season code like `'2627'`) and every fact row carries `season` with composite FKs. `RunMetadata.season` is required; the repository stamps it onto everything. Retention: all runs kept indefinitely by decision (no archival machinery).

## Implications for refactors

- Do not remove or "clean up" manual CSV input paths — generalise them (configurable path per gameweek, not hardcoded filenames like `player_minutes_inputs_gw37_to_38.csv`).
- The legacy CSV contract (`legacy_export.py`: filenames, column order) is load-bearing for both website and Admin Panel. Contract tests in `tests/test_model_contracts.py` guard it.
